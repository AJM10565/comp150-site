A secret about programmers

Professional programmers do not think in code. They think in English (or Spanish, or Polish…), and translate at the last possible moment.

The scary-looking algorithm is never the hard part. The hard part is saying precisely what you want — which you proved you can do two weeks ago, with a wolf, a goat, and a cabbage.

Tonight we turn that into a repeatable, three-step method.

The method

1 Say the steps in English — as comments, before any code exists

2 Write the code under each comment — each comment becomes a line or a small group

3 Play the computer — trace one input by hand until you've proved it works
English → code → proof. Notice what's missing: "stare at the blank cell until inspiration strikes." That step is cancelled, permanently.

Live: The Cash Register

The task: a customer is owed change. Hand it over using the fewest bills: 20s, 10s, 5s, 1s. Return how many of each.

Say it out loud: how do you make change for $48 in real life? You already run this algorithm — you've just never written it down.

Follow along in the lab notebook — this is the worked example at the top.

1 Comments only — code is illegal for the next 3 minutes

# start with the amount of change owed
# for each bill size, from largest to smallest:
#     figure out how many of that bill fits into what's left
#     reduce what's left by the value of those bills
# after the smallest bill, nothing should be left
Look at what just happened: the problem is already solved. No Python was harmed. If you can write these five lines, the rest is vocabulary.

2 Each comment gets its code

def make_change(amount):
    # start with the amount of change owed
    remaining = amount
    counts = []
    # for each bill size, from largest to smallest:
    for bill in [20, 10, 5, 1]:
        # figure out how many of that bill fits into what's left
        counts.append(remaining // bill)
        # reduce what's left by the value of those bills
        remaining = remaining % bill
    # after the smallest bill, nothing should be left
    return counts
Old friends in new jobs: // answers "how many fit?" and % answers "what's left?" — the same pair that turned 147 minutes into 2h 27m in the Week 3 lab.

Trace tables: the general recipe

Columns = every variable that changes, plus the loop's condition when it matters
Rows = one per step (per loop pass, usually)
Stop = when the program stops — not when the table runs out of rows
When to reach for one: a loop gives the wrong answer · a loop gives the right answer and you don't know why · before you run code you're unsure about · and on every exam you'll ever take in this building.

The two ways a loop does nothing

Trap A — the search that fails: your loop hunts for something… and it's not there. What does your function return? If the answer lives inside the loop, the answer is "nothing" — one of the most common bugs in all of programming.
Trap B — the loop that never starts: a while checks its condition before the first pass. If the condition is false on arrival, the body runs zero times — and your code must still be correct.
Both traps are in tonight's lab, hiding inside ⭐-marked tests. Your trace tables will walk you straight into them — on purpose, where it's cheap.

Addendum: Dictionaries

Labels, not positions

The last core data structure you need — if we have time tonight, or read-ahead for next week

Lists have a blind spot

You know this pain already. A list answers one question: "what's at position 3?"

But most real questions aren't positional: What's Hanna's grade? How many times did "error 429" appear? What's the price of oat milk?

With only lists, you end up managing two parallel lists — names in one, grades in another — and praying they never fall out of sync.
The missing tool: a container you look into by label instead of by position. That's a dictionary.

A dictionary is a set of label → value pairs

grades = {"Hanna": 25, "Vincent": 25, "Abbi": 24.75}

print(grades["Hanna"])      # 25   <- look up by label
grades["Abbi"] = 25         # change a value
grades["Jesse"] = 24.65     # add a brand-new pair
print(len(grades))          # 4
Vocabulary: the labels are called keys, the contents are values, each pair is an item. Curly braces { }, colon between key and value, commas between pairs.
Same square brackets as lists — but where a list wants [3], a dict wants ["Hanna"]. Position out, label in.

List vs Dictionary — same jobs, different questions

List — order matters 
temps = [70, 75, 76, 78]
temps[0]        # first reading
temps.append(69)
for t in temps:
    print(t)
Dict — labels matter 
menu = {"latte": 4.50,
        "drip": 2.75}
menu["latte"]   # by name
menu["mocha"] = 5.25
for drink in menu:
    print(drink, menu[drink])
Rule of thumb: a sequence of things → list. A lookup table of things → dict. (Sensor readings: list. Price sheet: dict. A gradebook: dict of name → score.)

The missing-key moment

menu = {"latte": 4.50, "drip": 2.75}

print(menu["mocha"])          # 💥 KeyError: 'mocha'

print("mocha" in menu)        # False  — check first, like lists
print(menu.get("mocha", 0))   # 0      — or supply a fallback
KeyError is the dictionary's version of last week's not-found problem: you asked for something that isn't there.
Two polite ways to ask: "mocha" in menu answers yes/no · menu.get("mocha", 0) answers "the value, or this default if missing." That second one is about to become the star of the show.

Looping over a dictionary

grades = {"Hanna": 25, "Vincent": 25, "Abbi": 24.75}

for name in grades:                      # keys
    print(name)

for name in grades:                      # keys -> values
    print(name, "scored", grades[name])

for name, score in grades.items():      # both at once
    print(name, "scored", score)
Everything you know about loops still applies — accumulate, count, find-the-biggest, trace tables. The loop variable just holds a key instead of a position's value.

The killer app: counting things

The task: count how many times each word appears in a list. With only lists, this is genuinely awkward. With a dict, it's four lines — and it's the single most-used pattern in data science.
votes = ["pizza", "tacos", "pizza", "sushi", "pizza", "tacos"]

counts = {}                                   # start empty
for v in votes:
    # current count if we've seen it, else 0 — then add this one
    counts[v] = counts.get(v, 0) + 1

print(counts)   # {'pizza': 3, 'tacos': 2, 'sushi': 1}
Read that middle line out loud: "the new count for this item is whatever it was before — or zero if it's new — plus one." .get(key, 0) makes the first sighting and the hundredth sighting the same line of code.

Trace tables work on dicts too — the "counts after" column is just a variable that happens to hold pairs. Watch the .get column: it's 0 exactly on first sightings.

Values can be anything — even lists, even dicts

student = {
    "name": "Hanna",
    "scores": [25, 12, 29.5],          # a list as a value
    "contact": {"email": "h@luc.edu"}  # a dict as a value
}

print(student["scores"][0])            # 25
print(student["contact"]["email"])     # h@luc.edu
Look familiar? This shape — labels, holding values, holding more labeled values — is exactly what JSON looks like: the format your AI harness config, every web API, and your Colab notebooks themselves are written in. When you read a .json file in Python, what you get back is a dictionary.

The fine print (small, but real)

Keys are unique. Assigning to an existing key replaces its value — that's why the counting pattern works.

Keys are usually strings or numbers. (Technically: anything unchangeable. Lists can't be keys.)

Values can repeat and can be anything.

Looking up by value takes a loop — dicts are one-directional: key → value is instant, value → key is a search (you wrote that search last week: it's first_above with different clothes).
Mental model that never fails: a real dictionary. Words (keys) are unique and looked up instantly; definitions (values) can be anything, and finding "which word means X" requires reading the whole book.

Putting it together: the gradebook, upgraded

# comments first, as always:
# start an empty gradebook
# for each (name, score) pair in the submissions:
#     record the score under the student's name
# then answer questions by label, not position

gradebook = {}
submissions = [("Hanna", 25), ("Vincent", 25), ("Abbi", 24.75)]
for name, score in submissions:
    gradebook[name] = score

print(gradebook["Vincent"])            # instant lookup
print(sum(gradebook.values()) / len(gradebook))  # class average
Two parallel lists just became one honest structure. .values() hands you the scores when you need list-style math — the tools compose.

Position → label

Lists answer "what's at spot 3?" · Dictionaries answer "what's Hanna's grade?"
Count with .get(key, 0) + 1 · check with in · loop with .items() — and trace when in doubt.
