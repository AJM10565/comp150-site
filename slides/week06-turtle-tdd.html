Part 1 — Dictionaries, a quick review

Last week's addendum, and the backbone of Assignment 4.

Labels, not positions

prices = {"milk": 3.25, "eggs": 2.10}

prices["milk"]          # 3.25   look up by key
prices["bread"] = 2.50  # add a new pair
prices["milk"] = 3.40   # update an existing key
len(prices)             # 3
A list answers "what's at position 2?" A dictionary answers "what's the price of milk?" Keys are unique; assigning to an existing key replaces its value.
🧪 Try it: what does prices["tea"] do? Predict, then run it in Colab.

Asking safely: in and .get

prices["tea"]            # 💥 KeyError: 'tea'
"tea" in prices          # False, so check first
prices.get("tea", 0)     # 0: the value, or a default if missing
.get(key, default) is the workhorse. It makes "never seen this key before" and "seen it a hundred times" the same line of code. You'll use it in every Assignment 4 problem.

Looping over a dictionary

for item in prices:                  # keys
    print(item)

for item, price in prices.items():   # keys and values together
    print(item, "costs", price)

for item in sorted(prices):          # keys in alphabetical order
    print(item)
Remember sorted(...): dictionaries keep insertion order, so when you need a predictable order (like breaking a tie alphabetically), loop over sorted(the_dict).

The counting pattern

votes = ["pizza", "tacos", "pizza"]
counts = {}
for v in votes:
    counts[v] = counts.get(v, 0) + 1   # old count (or 0) plus one
# counts == {"pizza": 2, "tacos": 1}
🧪 Try it: trace it by hand first. Make a table with columns v, counts.get(v, 0), and counts after. Three rows. Then run it and check.

Records: a list of dictionaries

visits = [
    {"patient": "A1", "symptom": "fever"},
    {"patient": "A2", "symptom": "cough"},
    {"patient": "A3", "symptom": "fever"},
]
for visit in visits:
    print(visit["symptom"])     # each record is a dictionary
This is what real data looks like: spreadsheet rows, API responses, sensor logs. Assignment 4's recipe is always two steps: organize the records into a dictionary (count, total, or group), then ask that dictionary a question (the biggest, the ones over a limit, and so on).

Part 2 — Meet the turtle

A turtle is a tiny robot holding a pen. It sits at the center of the canvas, point (0, 0), facing right. You give it instructions like "go forward 100" or "turn left 90", and it draws as it moves.

Every command is a function call, so everything you learned about loops and functions applies immediately.
In Colab: run !pip install -q ColabTurtlePlus then from ColabTurtlePlus.Turtle import * once, and start every drawing cell with clearscreen().

The coordinate system

x grows to the right, y grows up, and (0, 0) is the middle.
Headings: 0 = east · 90 = north · 180 = west · 270 = south.
The #1 surprise: circle(r) does not draw around the turtle. It starts at the turtle's spot, the bottom of the circle, and curves to the left. To center a circle on (x, y), start at (x, y - r).
🧪 Try it (lab): run setheading(90) then forward(100). Which way did it go? Then try 180 and 270.

Your first drawing: a loop

clearscreen()
setup(300, 300)
pencolor("blue")
for _ in range(4):
    forward(100)
    left(90)
A square is a loop. Four identical steps: go forward, turn 90°. The turtle ends up exactly where it started, facing the same way. That "return to start" is how you know the shape is closed.
🧪 Try it (lab): change 4 and 90 to draw a triangle, a pentagon, a hexagon. What's the rule? (All the turns add up to 360°.)

Change one number, get a new shape

penup(); goto(-80, 20); pendown()
pencolor("purple")
for _ in range(5):
    forward(160)
    right(144)
Why 144? A star's points skip around the circle. Five turns of 144° add up to 720°, exactly two full rotations, so the turtle closes the shape after looping around twice. Squares use 90° (4 × 90 = 360, once around).

Loops of shapes make patterns

pencolor("green")
for _ in range(12):
    circle(50)
    left(30)
12 circles × 30° = 360°. Draw one shape, rotate a little, repeat. Nearly every "fancy" turtle picture is this idea: a small loop inside a bigger loop.
🧪 Try it (lab): change the 12 and the 30 together. What has to stay true for the pattern to close?

The big idea: draw centered on a point

def draw_square(x, y, size, color):
    # jump to the bottom-left corner:
    # half the size left and down
    penup()
    goto(x - size / 2, y - size / 2)
    setheading(0)
    pendown()
    fillcolor(color)
    pencolor(color)
    begin_fill()
    for _ in range(4):
        forward(size)
        left(90)
    end_fill()
Both squares are centered on the same dot. When every shape function means "centered on (x, y)", you can place things precisely without trial and error. That's tonight's lab.

A picture is a list of dictionaries

house = [
  {"type": "rectangle", "x": 0, "y": -60,
   "width": 200, "height": 150, "color": "burlywood"},
  {"type": "triangle", "x": 0, "y": 60,
   "size": 230, "color": "firebrick"},
  ...
]
for spec in house:
    draw_shape(spec)
Data, not code. Each shape describes itself in a dictionary, and one loop draws them all. Want a sun? Add one dictionary; no new drawing code. This is how real graphics programs and games describe their scenes.

Optional: bundle data and behavior in a class

class Square:
    def __init__(self, x, y, size, color):
        self.x, self.y = x, y          # remember where I am
        self.size, self.color = size, color

    def draw(self):
        draw_square(self.x, self.y, self.size, self.color)

    def area(self):
        return self.size * self.size

roof_window = Square(0, 20, 30, "lightblue")
roof_window.draw()
A class is a dictionary that also knows how to act. The data (x, size, …) travels with its behavior (draw, area). It's optional this week, and it's especially handy when a picture has many shapes of the same kind.

Part 3 — Test-driven development

Until now I handed you the tests. From this week on, you write them, and you write them first.

A test is just a question you already know the answer to: "if I give cheapest_item milk $3.25, eggs $2.10, and bread $2.50, it should say eggs."

A friendlier test than assert

def test(expected, actual, test_name):
    """ Print the result of a test. """
    linenum = sys._getframe(1).f_lineno
    did_pass = expected == actual
    result = "PASSED" if did_pass else "FAILED"
    print(f"Test '{test_name}' at line {linenum} {result}.")
    if not did_pass:
        print(f"  Expected: {expected}")
        print(f"  Actual: {actual}")
assert just crashes: AssertionError, with no hint about what you got.
test() tells you: Test 'tie' at line 4 FAILED. · Expected: Ana · Actual: Cy. That's a clue, not a crash.

Why write the tests before the code?

1. It forces you to decide what "right" means before you're attached to your code. Ties? Empty input? You have to answer these first.

2. It gives you a finish line. You're done when the tests pass, not when you get tired.

3. It catches your own blind spots. Code written first tends to get tested only on the inputs it already handles.
You already do the English version: comments first, then code. TDD adds one more step before the code: examples of the right answer.

The loop: red → green → refactor

0. Plan: write your step comments in English.

1. Red: write your tests and run them. They fail, because the code isn't written yet. That proves your tests can catch a wrong answer.

2. Green: write the simplest code that makes the tests pass. Rerun. Fix. Repeat.

3. Refactor: clean up names and comments, rerun, and stay green.

Choosing tests: normal, special, edge

Normal: typical input. A few items with a clear answer.

Special: something that could trip up your logic. A tie, a repeat, a missing entry, a negative number.

Edge: the extremes. An empty list, a single item, exactly at a limit.
How many? There's no magic number: keep going until you can't think of an input that might break your function. And every test gets a comment saying why it's there. If you can't say why, it's probably a duplicate.

def cheapest_item(prices):
    # find the item with the lowest price
    # if two items tie, pick the one that comes first alphabetically
    # if there are no items, return None
    pass

# normal: three items with one clear cheapest
test("eggs", cheapest_item({"milk": 3.25, "eggs": 2.10, "bread": 2.50}), "normal")
# special: a tie must go to the alphabetically first item
test("apple", cheapest_item({"pear": 1.0, "apple": 1.0}), "special: tie")

Run it: red

Test 'normal' FAILED.
  Expected: eggs
  Actual: None
Test 'special: tie' FAILED.
  Expected: apple
  Actual: None
Test 'edge: empty' PASSED.
Two failures: good. The code does nothing yet, and the tests noticed.
But look at the edge test: it passes against an empty function. A test that passes before you've written any code isn't proving much by itself. Keep it, but don't let it be your only test.

Step 2 (green), first attempt

def cheapest_item(prices):
    best = None
    for item in prices:
        if best is None or prices[item] < prices[best]:
            best = item
    return best
Test 'normal' PASSED.
Test 'special: tie' FAILED.
  Expected: apple
  Actual: pear
Test 'edge: empty' PASSED.
The tie test caught a real bug. The normal test would never have found it. Pear came first in the dictionary, and < never replaces a tie.

Fix, rerun, green

def cheapest_item(prices):
    best = None
    for item in sorted(prices):      # visit items alphabetically, so ties go to the first name
        if best is None or prices[item] < prices[best]:
            best = item
    return best
Test 'normal' PASSED.
Test 'special: tie' PASSED.
Test 'edge: empty' PASSED.
Green. Now refactor if you like (better names, clearer comments) and rerun to stay green. That's the whole loop, and it's exactly what each Assignment 4 problem asks you to do.
